# Инструкция для агента на другом устройстве

Задача: локально обработать ТОЛЬКО переданную группу фотографий, сохранить CSV и базу
для продолжения. Полный исходный архив содержит 940 фото, разделён на part_1 и part_2
по 470. Оригиналы находятся отдельно; входные копии также нельзя изменять/переименовывать.
Фотографии, миниатюры, GPS и описания не отправлять в облачные API/vision/Codex и
не открывать средствами vision агента. Изображения читает локальная Ollama.

## Что перенести

1. Код клонировать из GitHub-репозитория этого проекта.
2. Передать свою папку part_1 ИЛИ part_2 отдельным локальным/разрешённым пользователем
   каналом; НЕ через GitHub. Сохранить внутренние имена и структуру подпапок.
3. Передать соседний part_1_manifest.json или part_2_manifest.json для контроля хешей,
   но положить его рядом с входной папкой, а не внутрь: импорт регистрирует все файлы.
4. Веса Ollama, .venv и work с другого Windows-устройства не копировать как окружение:
   Python/зависимости установить на целевой системе. Для продолжения той же группы можно
   переносить её workspace при остановленной обработке, включая все SQLite/WAL-файлы.
   При изменении пути к фото безопаснее новый импорт в новой базе; CSV сохраняет прежние ID.

## Установка и диагностика

Python 3.11+, Windows/PowerShell; желательно NVIDIA GPU. Объём VRAM второго устройства
измерить, а не предполагать по названию карты. Из корня клона:

```powershell
git clone https://github.com/reSMX/kemerovo-city-photo.git
Set-Location kemerovo-city-photo
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
ollama pull qwen3-vl:4b-instruct-q4_K_M
.\.venv\Scripts\python.exe -m pytest -q
.\run.ps1 doctor
```

Установить/запустить Ollama, если отсутствует. Анализ обращается только к
http://127.0.0.1:11434, по одному запросу. Для запрета облака самой Ollama можно запустить
её с OLLAMA_NO_CLOUD=1. Сеть нужна только для установки, весов и отдельной подготовки карты.
Модель по умолчанию — Instruct. В выполненном на первом устройстве сравнении она дала
валидный ответ 12/12, Thinking 11/12. Не подменять модель скрыто. До совместного производственного запуска пользователь
может выбрать другую модель по ручному сравнению: зафиксировать ОДИН тег/digest,
рубрику, промпт и настройки на обоих устройствах.
Для итогового балла также согласовать photo_scoring.yaml; он описан в SCORING.md.
После изменения весов достаточно export, без нового инференса.

На 16 ГБ RAM не держать обе модели загруженными одновременно. Скрипт compare_models.py
выгружает предыдущий из двух сравниваемых вариантов через keep_alive=0, не удаляя веса.
При системной ошибке нехватки файла подкачки проверить доступную RAM/виртуальную память;
не увеличивать контекст вслепую и не подменять ошибку нулевыми оценками.

## Настройка группы и запуск

Пример ниже для part_2, расположенной на D:. Если путь другой — изменить только путь
в копии YAML и InputFolder, не имена внутри папки. Workspace и OutputFolder выделить
отдельно для каждой группы. Карта опциональна; без карты визуальный анализ работает.

```powershell
Copy-Item config.example.yaml config.part2.yaml
# В config.part2.yaml задать input: D:/map_photos_split/part_2
# Остальные параметры, prompts/assessment.txt и rubric.yaml согласовать с первым устройством.
.\.venv\Scripts\python.exe split_photos.py --input D:\map_photos_split\part_2 --verify-manifest D:\map_photos_split\part_2_manifest.json
.\run.ps1 prepare -InputFolder D:\map_photos_split\part_2 -Workspace work_part2 -OutputFolder output_part2 -Config config.part2.yaml
.\run.ps1 sample -Workspace work_part2 -OutputFolder output_part2 -Config config.part2.yaml
```

Проверить CSV на первых 20 файлах и расход GPU. При нехватке памяти используется один
ограниченный повтор с меньшим размером/контекстом; это фиксируется как degraded.
Не выдавать отсутствие ошибок за доказательство точности оценок. Ориентация исправляется
по EXIF, затем проверяется локальной моделью; спорные случаи отправляются на проверку.

Продолжение всей СВОЕЙ группы:

```powershell
.\run.ps1 all -Workspace work_part2 -OutputFolder output_part2 -Config config.part2.yaml
# Новые фото или перезапуск после добавления:
.\run.ps1 update -InputFolder D:\map_photos_split\part_2 -Workspace work_part2 -OutputFolder output_part2 -Config config.part2.yaml
# Повторить только ошибки:
.\run.ps1 retry -Workspace work_part2 -OutputFolder output_part2 -Config config.part2.yaml
```

Для part_1 заменить пути и суффиксы на part1. Ctrl+C сохраняет завершённые записи.
Не использовать --force при обычном продолжении. Сохранять work_part2: кэш и SQLite
позволяют не анализировать повторно неизменённые фото. При смене рубрики/модели/параметров
кэш намеренно инвалидируется, чтобы старые оценки не выдавались за новые.

## Что вернуть пользователю

`output_part2/results.csv`, `review.csv`, `run_summary.json`, `data_dictionary.md`,
точный commit кода, digest модели и параметры. SQLite/derived/raw остаются локальными,
переносятся отдельно по запросу пользователя; не публиковать в GitHub. В отчёте указать
число processed/model_error/pending, среднее время, нарушения ориентации/деградации и
проверялась ли точность вручную.

## Объединение двух устройств

Положить results.csv каждой группы в разные папки на одном устройстве:

```powershell
.\.venv\Scripts\python.exe merge_results.py --inputs output_part1/results.csv output_part2/results.csv --output merged/results.csv
```

Скрипт откажется при пересечении идентификаторов/путей или разных версиях модели,
промпта и рубрики. Он сохраняет строки ошибок и не усредняет фото. Итог при полном
покрытии должен содержать 940 строк. Разные локальные входные пути допустимы.
`--allow-mixed` использовать только для намеренно маркированного смешанного экспорта;
обычный совместный анализ проводить с согласованными версиями и настройками.
